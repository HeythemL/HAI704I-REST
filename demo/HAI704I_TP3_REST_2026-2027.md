## OBJECTIF

Construire, de bout en bout, une application distribuée en REST sur HTTP : des hôtels exposent chacun leur API, une agence de voyage les interroge tous, applique sa marge et publie à son tour son API, et un comparateur agrège plusieurs agences. Le CM 04 a posé le style et le protocole ; il s’agit maintenant de les mettre en œuvre. Chaque étape :

- pose une décision de conception : que nomme-t-on comme ressource, quelle méthode porte l’intention, quel code de statut dit la vérité ?

- se termine par un résultat observable : une réponse HTTP, un en-tête, un refus, une réservation qui survit à un redémarrage.

## A0 Mise en route : consommer une API publique, à la main

Avant d’exposer quoi que ce soit, il faut avoir observé des échanges HTTP réels. Les services tiers ci-dessous sont publiques, servent à regarder, ne demandent ni compte ni clé, et aucun point du TP n’en dépend.

## A0.1 — UNE API PUBLIQUE FRANÇAISE

La Géoplateforme de l’IGN expose un service de géocodage ouvert.

- 1. Appelez https://data.geopf.fr/geocodage/search/?q=montpellier&limit=1 avec curl -i. Relevez la méthode, l’URI, le code de statut, les en-têtes de réponse et le corps.

- 2. Recommencez avec curl -v : vous voyez cette fois ce que votre client envoie. Repérez l’en-tête Accept qu’il ajoute tout seul.

- 3. Retirez le paramètre q. Lisez le code de statut et le corps : le service vous dit quoi corriger. Comparez avec un service qui répondrait « erreur ».

- 4. Repérez l’en-tête ETag de la première réponse, puis redemandez la même URI en ajoutant -H ’If-None-Match: <la valeur>’. Que change le code de statut ? Que devient le corps?

## A0.2 — OBSERVER LE PROTOCOLE LUI-MÊME

- 1. Sur https://api.github.com/repos/spring-projects/spring-boot, relevez ETag, Cache-Control et les en-têtes X-RateLimit-*. Rejouez avec If-None-Match et observez le 304.

- 2. Demandez un dépôt qui n’existe pas. Le 404 porte un corps : lisez-le.

- 3. Sur https://httpbingo.org, envoyez successivement GET, POST, PUT, PATCH et DELETE sur /get, /post, /put, /patch, /delete. Le service vous renvoie votre propre requête : c’est le meilleur moyen de voir ce que curl a réellement émis.

- 4. Toujours sur httpbingo.org, obtenez délibérément un 409, un 422 et un 503 via /status/409, /status/422, /status/503.

## A0.3 — LE MÊME ÉCHANGE, EN GRAPHIQUE

Refaites au moins trois des appels ci-dessus avec Postman, et retrouvez-y, à l’écran, chacun des éléments que curl -i affiche : méthode, URI, paramètres, en-têtes de requête, code de statut, en-têtes de réponse, corps. L’annexe 1 fait la correspondance point par point.

## A2 L’API de l’hôtel : lecture, et une photo

## A2.1 — LE PROJET ET LES OFFRES

- 1. Créez le projet de l’hôtel sur start.spring.io (voir l’annexe 1 pour les choix exacts).

- 2. Exposez la recherche d’offres comme une lecture de collection, filtrable par ville, dates et nombre de personnes.

- 3. Exposez la consultation d’une offre par son identifiant, et le 404 correspondant.

- 4. Rendez la collection sous une enveloppe pour pouvoir y ajouter plus tard pagination et liens sans casser vos clients.

- 5. Séparez dès maintenant trois choses : la représentation rendue au client (DTO), le type du métier, et plus tard l’entité de persistance. L’annexe 2 montre les trois côte à côte.

## A2.2 — LA PHOTO DE LA CHAMBRE

Une offre doit pouvoir montrer une image de la chambre.

- 1. Exposez-la comme une sous-ressource dédiée, par exemple GET /api/v1/offres/{id}/photo.

- 2. Rendez-la avec le bon Content-Type, un Content-Length juste, et un ETag.

- 3. Faites apparaître, dans la représentation JSON de l’offre, un lien vers cette photo.

- 4. Demandez la photo en envoyant Accept: application/json. Expliquez le code que vous obtenez, et pourquoi il est correct.


## POURQUOI PAS L’IMAGE EN BASE64 DANS LE JSON?

C’est possible, et c’est presque toujours un mauvais choix par défaut : l’encodage gonfle la charge d’environ un tiers, oblige à transporter l’image même quand le client n’en veut pas, et prive tout intermédiaire de la possibilité de mettre l’image seule en cache. Le base64 dans le corps peut être éventuellement défendu quand l’image et ses métadonnées doivent voyager en une seule écriture atomique, mais c’est un cas limite pas forcément obligé dans notre contexte.

## POINT DE CONTRÔLE A2

curl -i sur la collection rend 200 et une enveloppe ; sur une offre inconnue, 404 ; la photo arrive avec son type de média, sa longueur et son ETag, et l’offre JSON y renvoie. Votre représentation n’expose aucun champ qui n’appartient qu’au stockage.

## A3 Quand l’hôtel refuse : la sémantique HTTP des erreurs

## TRAVAIL DEMANDÉ

- 1. Centralisez le traitement des fautes dans un @RestControllerAdvice, et rendez toutes vos erreurs en application/problem+json au format de la RFC 9457 (ProblemDetail).

- 2. Validez les représentations entrantes. Distinguez un corps illisible d’un corps syntaxiquement correct mais inacceptable ; ce ne sont pas le même code.

- 3. Pour chacun des codes que votre conception A1 prévoit, provoquez-le délibérément avec curl et conservez le relevé. Au minimum : 400, 404, 405, 409, 415, 422.

- 4. Vérifiez que votre 405 porte bien un en-tête Allow, et dites d’où il vient.

## CHAQUE CODE DOIT CORRESPONDRE À UNE SITUATION RÉELLE

On attend que chaque code que vous rendez soit justifié par une situation concrète de votre application, et que vous sachiez dire pourquoi ce n’est pas le code voisin : 401 n’est pas 403, 400 n’est pas 422, 404 n’est pas 409.

## POINT DE CONTRÔLE A3

Chaque erreur de votre API sort en problem+json avec un type, un title, un status et un detail utile ; vous avez un relevé curl par code ; vous savez justifier chaque choix de code.

## A4 L’agence : un client REST explicite

## TRAVAIL DEMANDÉ

- 1. Créez le projet de l’agence, séparé de celui de l’hôtel.

- 2. Consommez l’API de l’hôtel avec RestClient, construit par injection de constructeur.

- 3. Votre client doit lire le code de statut et les en-têtes, pas seulement désérialiser un corps de succès.

- 4. Traduisez les échecs distants dans le vocabulaire de l’agence : un hôtel injoignable, un hôtel lent et un hôtel qui répond 500 sont trois incidents différents.

- 5. Fixez des délais d’attente explicites. Un client sans délai est un client qui attend indéfiniment.

- 6. Gardez le code de transport séparé du métier : aucune classe métier de l’agence ne doit importer quoi que ce soit de Spring Web.

## CE QUE VOTRE CLIENT NE DOIT PAS FAIRE

Pas d’adresse de service dans une variable statique modifiable. Pas de Thread.sleep pour « laisser le temps » au serveur. Pas de System.exit au fond d’un bean. Pas de couche client qui rende les codes de statut invisibles à l’appelant : c’est le défaut qui rend un système réparti impossible à diagnostiquer.


## POINT DE CONTRÔLE A4

L’agence, dans son propre processus, obtient les offres d’un hôtel ; elle distingue un succès, un refus métier et une panne ; un hôtel arrêté ne provoque ni trace d’exception brute ni blocage indéfini.

## A5 Réserver : écriture, authentification, idempotence et concurrence

## A5.1 — CRÉER UNE RÉSERVATION

- 1. L’hôtel expose la création d’une réservation. La réponse porte le code de création et l’en-tête qui donne au client l’URI de ce qui vient d’être créé.

- 2. Cette URI doit être lisible : un GET dessus rend la réservation.

- 3. L’hôtel authentifie l’agence. Une agence inconnue est refusée avec le code qui dit « authentifiez-vous », assorti de l’en-tête que le protocole exige.

- 4. Réserver une offre déjà prise ne rend pas la même chose que réserver une offre inexistante. Justifiez les deux codes.

## A5.2 — LE REJEU NE DOIT PAS CONSOMMER DEUX FOIS

Le réseau perd des réponses : une agence qui n’a rien reçu réémet. Si chaque réémission crée une réservation, vous réservez la même chambre plusieurs fois.

- 1. Faites accepter à l’hôtel une clé d’idempotence fournie par l’agence.

- 2. Une seconde demande portant la même clé rend la même réservation, sans consommer la chambre une seconde fois. Le code de statut doit refléter qu’il n’y a pas eu création.

- 3. Propagez la clé depuis le comparateur jusqu’à l’hôtel, à travers l’agence.

- 4. Démontrez-le : deux appels identiques, une seule réservation.

## A5.3 — MODIFIER SANS ÉCRASER LE TRAVAIL D’UN AUTRE

- 1. Donnez à la réservation un ETag qui change à chaque modification.

- 2. La modification exige une condition portant sur cet ETag.

- 3. Une condition fausse (parce qu’un autre a modifié entre-temps) est refusée avec le code prévu pour cela, et non écrasée en silence.

- 4. Offrez l’annulation. Dites en quoi son effet est idempotent, et pourquoi cela ne signifie pas que toutes les réponses portent le même code.

## POINT DE CONTRÔLE A5

Une réservation se crée, s’obtient à l’URI annoncée, se modifie sous condition et s’annule ; une agence non authentifiée est refusée ; le rejeu d’une même clé ne crée pas de doublon ; une modification fondée sur un état périmé est refusée.

## A6 Plusieurs hôtels : composer, et survivre aux défaillances

## TRAVAIL DEMANDÉ

- 1. L’agence interroge plusieurs hôtels, dont la liste est configurable : ajouter un hôtel ne doit demander aucune recompilation.

- 2. Lancez trois hôtels : un normal, un lent (au-delà de votre délai d’attente), un arrêté.

- 3. L’agence doit rendre un résultat partiel utile : les offres obtenues, et la liste nommée de ce qui a échoué, avec la cause.

- 4. Faites répondre 500 à un hôtel et vérifiez que l’agence le traite comme un incident de ce fournisseur, et non comme sa propre faute.


- 5. Quand l’agence ne peut rien rendre à cause de l’amont, le code qu’elle rend doit dire que le problème est en amont.

## C’EST LE CŒUR DU TP

Un système réparti n’a pas deux états, debout et en panne ; il a des états partiels. Si trois hôtels sont interrogés et qu’un seul est tombé, rendre une erreur globale revient à jeter deux réponses valides. Cacher la défaillance est encore pire parce qu’une liste silencieusement incomplète ne dit pas ce qui s’est passé réellement.

## POINT DE CONTRÔLE A6

Avec un hôtel arrêté et un hôtel lent, l’agence répond vite, rend les offres de l’hôtel debout, et dit explicitement lesquels n’ont pas répondu et pourquoi.

## A7 L’API de l’agence, et le comparateur

## TRAVAIL DEMANDÉ

- 1. L’agence publie à son tour son API REST : elle est un serveur pour le comparateur et un client pour les hôtels.

- 2. Elle applique sa marge : le prix qu’elle publie n’est pas celui de l’hôtel. Le prix de base ne doit pas fuiter dans sa représentation.

- 3. Ses identifiants d’offre doivent rester exploitables alors que deux hôtels peuvent employer les mêmes.

- 4. Le comparateur interroge plusieurs agences, agrège leurs offres et les présente classées.

- 5. Lancez deux agences aux marges différentes : la même chambre doit apparaître à deux prix.

- 6. Le comparateur survit à une agence absente, exactement comme l’agence survit à un hôtel absent.

## NE REPLIEZ PAS LES TROIS NIVEAUX EN UN SEUL

Hôtels, agence et comparateur sont des processus distincts qui ne partagent ni code métier ni base de données. Une application Spring unique contenant trois paquetages et une seule base ne répond pas à la question, même si elle produit le même affichage.

## POINT DE CONTRÔLE A7

Au moins deux hôtels, deux agences et un comparateur tournent simultanément dans des processus séparés ; la même chambre apparaît à deux prix selon l’agence ; arrêter une agence n’empêche pas le comparateur de rendre le reste.


## A8 Une application utilisable, et sa persistance

## A8.1 — DE LA MÉMOIRE À JPA/H2

Jusqu’ici, un dépôt en mémoire était suffisant pour régler le comportement HTTP sans vous battre avec une base. Il est temps de le remplacer.

- 1. Vos dépôts sont déjà derrière une interface. Ajoutez-en une seconde réalisation, fondée sur Spring Data JPA et H2.

- 2. L’entité de persistance n’est pas la représentation HTTP. Elle ne doit apparaître ni dans un contrôleur, ni dans une réponse.

- 3. Aucune classe du métier, du contrôleur ou des représentations ne change. Si ce n’est pas le cas, votre frontière n’était pas au bon endroit.

- 4. L’application finale rendue utilise JPA/H2. Montrez que les réservations survivent à un redémarrage du service.

## A8.2 — L’INTERFACE EN LIGNE DE COMMANDE

- 1. Écrivez une CLI qui permet de (i) chercher et consulter des offres, et de (ii) réserver et retrouver une réservation. Vous en concevez le dialogue.

- 2. Elle doit permettre un vrai parcours utilisateur, et non dérouler une suite d’appels écrits en dur.

- 3. Elle ne construit aucune URL et ne connaît aucun code de statut ; cela vit dans la couche client.

- 4. Écrivez des tests automatisés du métier, sans réseau ni base.

- 5. Rejouez la chaîne complète de bout en bout, tous processus séparés, et conservez la trace.

## POINT DE CONTRÔLE A8

L’application finale persiste en JPA/H2 et survit à un redémarrage ; la CLI permet un parcours complet ; les tests passent ; la chaîne comparateur  agence  hôtel fonctionne en processus séparés.
