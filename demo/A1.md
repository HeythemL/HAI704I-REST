# Étape A1 — Du besoin aux ressources : Concevoir avant de coder

> **Contexte** : Architecture distribuée à trois niveaux (Comparateur ➔ Agence(s) ➔ Hôtel(s)).  
> Ce document constitue la conception formelle de l'architecture REST requise pour le rapport final (`Compte-Rendu.pdf`).

---

## 1. Identification des Ressources et Justifications

Une ressource REST est une entité conceptuelle identifiable, adressable par un identifiant uniforme (URI), et sur laquelle s'appliquent les opérations standardisées du protocole HTTP.

### Ressources retenues
1. **`Offre` / `Offres` (`/api/v1/offres`)** :
   * *Pourquoi est-ce une ressource ?* Une offre représente une proposition commerciale disponible d'un hôtel (ou d'une agence avec marge) pour un type de chambre donné sur une période donnée. Elle a une durée de vie, peut être identifiée de manière unique, consultée, comparée et mise en cache.
2. **`Photo` d'une offre (`/api/v1/offres/{id}/photo`)** :
   * *Pourquoi est-ce une ressource ?* La photo est un média binaire distinct (`image/jpeg`) rattaché à une offre. Elle possède un cycle de vie, des caractéristiques de mise en cache (`ETag`, `Cache-Control`) et un type de contenu différents de la représentation JSON de l'offre.
3. **`Reservation` / `Reservations` (`/api/v1/reservations`)** :
   * *Pourquoi est-ce une ressource ?* Une réservation modélise un engagement contractuel entre un client (ou une agence pour son compte) et l'hôtel. Elle possède un cycle de vie complet : création, consultation, modification de séjour, et annulation.

### Ce qui n'est PAS une ressource (et justification)
- **La recherche d'offres (`/chercherOffres`)** : La recherche n'est pas une entité persistante autonome. C'est simplement une consultation de la collection `Offres` avec filtrage (`GET /api/v1/offres?ville=...`).
- **Le calcul de marge de l'agence** : C'est une règle de gestion interne du domaine métier de l'agence, pas un objet exposé sur le web.
- **L'authentification / Le mot de passe** : L'authentification est portée par les en-têtes HTTP du protocole (ex. `Authorization: Basic ...` ou tokens), et non par une ressource REST mutable.

## 2. Conception des URI et Conventions

- **Noms au pluriel** : Les collections sont désignées par des noms communs au pluriel (`/offres`, `/reservations`) pour désigner l'ensemble des éléments gérés.
- **Identifiant dans le chemin** : Les ressources individuelles utilisent un identifiant unique opaque dans le chemin (`/offres/{id}`, `/reservations/{id}`).
- **Hiérarchie / Sous-ressources** : L'accès à la photo d'une offre reflète la relation de composition (`/offres/{id}/photo`).
- **Paramètres de requête (`Query Params`) pour le filtrage** : Les critères de recherche (`ville`, `dateDebut`, `dateFin`, `nbPersonnes`) filtrent la collection sans altérer l'identité de la ressource.
- **Gestion de version** : Préfixe `/api/v1/` garantissant l'évolutivité de l'API sans rompre les contrats existants.

| :--- | :--- | :---: | :--- | :---: | :---: | :---: | :--- |

| **Réservation individuelle** | `/api/v1/reservations/{id}` | `PUT` | Modification complète d'une réservation existante sous condition de concourance (`If-Match: ETag`). | **Non** | **Oui** | `200 OK` | `400 Bad Request` (syntaxe invalide)<br>`404 Not Found` (réservation inexistante)<br>`412 Precondition Failed` (l'ETag fourni ne correspond plus : modification concurrente détectée)<br>`428 Precondition Required` (en-tête `If-Match` absent) |

> **Rappels normatifs HTTP :**
> - **Sûre** : La méthode n'a aucun effet de bord modifiant l'état du serveur (`GET`, `HEAD`, `OPTIONS`).
> - **Idempotente** : Exécuter la requête $N$ fois a le même effet sur l'état du serveur qu'une seule exécution (`GET`, `PUT`, `DELETE`).

## 4. Représentation des Ressources (Champs Exposés vs Cachés)

### 4.1. Représentation d'une `Offre` (`application/json`)
- **Enveloppe collection (`GET /api/v1/offres`)** :
  Toujours encapsulée dans un objet JSON (`{ "offres": [...], "_links": { ... }, "total": 12 }`) afin de permettre l'ajout ultérieur de pagination et de métadonnées sans casser les contrats clients.
- **Champs exposés dans le DTO** :
  - `id` : Identifiant public/commercial de l'offre (ex: `HOTEL1-OFFRE-42` ou UUID côté agence).
  - `nomHotel` : Nom de l'établissement.
  - `ville` : Localisation.
  - `typeChambre` : Simple, double, suite...
  - `capacite` : Nombre de personnes.
  - `dateDebut`, `dateFin` : Période de disponibilité.
  - `prixTotal` : Prix public facturé au client.
  - `_links` : Liens HATEOAS (vers l'offre elle-même, vers la photo).
- **Champs cachés (Strictement non exposés)** :
  - La clé primaire auto-incrémentée interne de la base de données (`id_pk` DB).
  - Le chemin absolu du fichier de l'image sur le disque du serveur (`/var/data/storage/chambre_101.jpg`).
  - Le pourcentage ou montant de la marge appliquée par l'agence.
  - Le prix d'achat initial brut consenti par l'hôtel à l'agence (ce prix ne doit jamais fuiter dans la réponse de l'agence vers le comparateur).

### 4.2. Représentation d'une `Reservation` (`application/json`)
- **Champs exposés** :
  - `id` : Identifiant de réservation.
  - `offreId` : Référence vers l'offre réservée.
  - `nomClient` : Nom du voyageur.
  - `dateDebut`, `dateFin` : Dates réservées.
  - `statut` : `CONFIRMED`, `CANCELLED`.
  - `prixPaye` : Montant total convenu.
  - `_links` : Liens vers la réservation (`self`) et l'offre associée.
- **Champs cachés** :
  - Coordonnées bancaires ou tokens sensibles.
  - Mots de passe / secrets de l'agence partenaire.
  - Flags de verrouillage interne de base de données.

## 5. Relations entre Ressources et Liens (HATEOAS)

Les ressources ne sont pas isolées : leurs liens de navigation sont explicités dans la représentation JSON.

Exemple de réponse pour `GET /api/v1/offres/H1-42` :
```json
{
  "id": "H1-42",
  "nomHotel": "Grand Hôtel de Paris",
  "ville": "Paris",
  "typeChambre": "Double Deluxe",
  "capacite": 2,
  "prixTotal": 240.00,
  "dateDebut": "2026-12-01",
  "dateFin": "2026-12-05",
  "_links": {
    "self": {
      "href": "/api/v1/offres/H1-42"
    },
    "photo": {
      "href": "/api/v1/offres/H1-42/photo",
      "type": "image/jpeg"
    },
    "reserver": {
      "href": "/api/v1/reservations",
      "method": "POST"
    }
  }
}
```

## 6. A1.2 — Analyse Critique de l'Anti-Modèle (RPC sur HTTP)

Un camarade propose l'interface suivante :
- `POST /chercherOffres`
- `POST /reserverChambre`
- `POST /annulerReservation`

### 1. Ce que cette conception fait perdre concrètement :

1. **Perte de la mise en cache HTTP intermédiaire** :
   - Selon la spécification RFC 9110, les requêtes `POST` ne sont par défaut jamais mises en cache par les proxys intermédiaires, CDN et navigateurs. Remplacer `GET /api/v1/offres?...` par un `POST /chercherOffres` force chaque consultation identique à traverser tout le réseau jusqu'à la base de données, saturant inutilement les services.
2. **Perte de l'adressabilité et du bookmarking client** :
   - Une requête `GET` encode ses paramètres dans l'URI (`/api/v1/offres?ville=Paris&nbPersonnes=2`). Un utilisateur ou un système tiers peut copier ce lien, le partager, l'enregistrer en favori ou l'utiliser comme clé de rafraîchissement. Avec un `POST`, les critères sont enfouis dans le corps opaque : l'URL est générique (`/chercherOffres`) et inexploitable isolément.
3. **Perte de la rejouabilité sans risque (Idempotence & Safety)** :
   - `annulerReservation` avec `POST` n'est pas déclarée idempotente au niveau protocolaire. En cas de perte de réseau (timeout), le client ne sait pas si l'annulation a été traitée. S'il réémet un `POST`, il risque de déclencher des erreurs non voulues. Avec `DELETE /api/v1/reservations/{id}`, la sémantique HTTP garantit que supprimer une ressource déjà supprimée produit le même état final.
4. **Violation des codes de statut standardisés** :
   - `POST /chercherOffres` répond généralement `200 OK` même si rien n'est trouvé, ou masque les erreurs dans des corps JSON personnalisés (`{ "status": "error" }`), rendant aveugles les passerelles de supervision réseau (API Gateway, reverse-proxies).

### 2. Dans quel cas un `POST` d'action reste-t-il le bon choix ?
Un `POST` d'action (procédural ou "controller pattern") est légitime lorsqu'une opération métier :
- **Ne correspond à aucun cycle de vie CRUD direct d'une ressource persistante** : par exemple, déclencher un virement bancaire ou un appel à une passerelle de paiement tierce (`POST /api/v1/paiements/valider`).
- **Engendre des effets de bord multiples et complexes non modélisables par un simple changement d'attribut** : par exemple, `POST /api/v1/ordonnanceur/nettoyage-nocturne` ou l'exécution d'un calcul distribué lourd à la volée.
